第一幕：有多痛（2 分鐘）

【痛點一：單份合約很耗時】

我們先看一個數字。LawGeex 曾經做過一個研究——請 20 位執業律師盲測審閱同一份 NDA（保密協議）。

結果是：平均 92 分鐘。

92 分鐘。只是一份 NDA。

現在問各位在座的：你們公司一年簽多少份合約？肯定不止 1 份。

【痛點二：年度累積是災難】

LegalOn 在 2025 年對 286 位法務人員的調查顯示：

52% 的企業每年簽 101 到 1,000 份合約，平均每份耗費 2 到 4 小時。

一個典型的 3 人法務團隊，一年簽 500 份合約。

按照 3.1 小時 / 份來算，就是 1,550 小時。

一個人一年 250 個工作天，8 小時 / 天，就是 2,000 小時。

1,550 小時意味著什麼？意味著一個 3 人團隊的 75% 時間都在審合約。

剩下 25% 才是真正的法律判斷、協商、合規工作。

【痛點三：錯過合約審查，損失是巨額的】

如果因為審查慢而延誤了呢？

Gartner 計算過：新產品因為合約審查延遲 6.5 天，一個大型企業會損失 700 萬美元的營收。

700 萬美元！

而且，WorldCC 的研究更驚人：合約管理不善，企業會流失高達 9.2% 的年營收。

想象一家 10 億營收的公司，因為合約管理問題，流失 9,200 萬。

【痛點四：台灣企業同樣面臨】

這不是國外才有的問題。工研院、勤業眾信、先行智庫都證實：台灣企業同樣面臨版本控管混亂、法務審查瓶頸。

而且，52% 的企業仍然用 email + Word 共用資料夾管理合約版本。

想象一下：版本 1、版本 2、版本 3、版本 4，都在 email、Slack、Drive 裡散落……法務怎麼知道現在該簽哪一份？

【問題的根源】

現在的問題是：有沒有 AI 工具能自動做？有。但是……

純 LLM 方案（ChatGPT、Claude）：速度快，但容易編造、容易遺漏高風險——而且是黑盒，法務看不到判斷根據。

純規則引擎：邏輯清楚，但規則寫不完。「千分之一違約金」和「0.3% 費率」是同一回事，規則怎麼判？

所以，我們的做法不一樣。

【流程圖講解 — 簡潔工作流 + Case A/B/C 去重複邏輯】

看一下我們的核心工作流程。這裡面有個關鍵的去重複邏輯。

第一步：自動掃描（1 分鐘）

  • 系統拿到新舊合約版本，用 LCS 和 Needleman-Wunsch 演算法自動比對
  • 找出所有改動：新增、修改、刪除
  • 1 分鐘完成

第二步：雙軌風險判斷（這是關鍵）

  • 同時啟動兩個判斷引擎
    • ✓ Rule Engine：用 15 條規則做確定性判斷，100% 不漏判高風險
    • LLM Agent：看規則看不懂的邊界案例，用語意理解補充風險
  • 重點：它們各自判斷，結果可能一致，也可能分歧

第三步：交叉核對 + Case A/B/C 邏輯（去重複的關鍵）

  • Case A：都發現同一個風險

    • 例：責任上限縮小，規則發現 ✓，Agent 也發現 ✓
    • 結果：去重複，保留規則版本（規則已驗證 100% 正確）
    • 來源標籤：✓ 規則引擎

  • Case B：只有規則發現

    • 例：保護條款被刪，規則發現 ✓，Agent 沒發現（可能被其他文字干擾）
    • 結果：保留規則版本（幸好規則沒漏）
    • 來源標籤：✓ 規則引擎

  • Case C：只有 Agent 發現（這是 AI 的補漏所在）

    • 例：違約金改為「千分之一」，規則看不懂 ✗，Agent 理解費率降 66.7% ✓
    • 結果：標記為 ⚠️ Agent 補漏
    • 來源標籤：⚠️ Agent 補漏（法務看到這個標籤，知道要額外審視）

為什麼要標籤？ 因為法務要知道「這個風險是規則找的（已驗證）還是 AI 補的（需要你確認）」。

第四步：生成報告

  • 自動產出風險旗標表（高/中/低，附來源欄）
  • 自動產出三層協商方案（🟢 首選、🟡 折衝、🔴 底線）
  • 自動產出協商矩陣（可直接列印帶去談判）

整個流程：1 分鐘 AI 初審 + 30 分鐘法務確認 = 1 小時完成

對比傳統人工？從 2 小時變 1 小時，時間減半。

【架構圖講解 — 完整系統設計】

現在讓我深入說明系統怎麼設計成這麼可靠。

我們採用四層 + 橫向保護的架構：

Layer 1：Rule Engine（確定性層）

  • 15 條預定義規則：責任上限變更、保護條款刪除、費率改動等
  • 這些規則是從真實合約場景萃取的，不是憑空編造
  • 驗證結果：38 筆人工標註合約，高風險 5/5 全發現（100% recall），整體偵測率 54%（12/22）
  • 作用：確保沒有遺漏

Layer 2：Verification Agent（補漏層）

  • LLM 專門看規則看不懂的邊界案例
  • 例子：「千分之一違約金」——規則用 Regex 無法判斷，但 LLM 能理解這是「費率降 66.7%」
  • 作用：補充規則的盲點

Layer 1.5：MAS 多視角驗證（審核層）— Agent A/B 多視角邏輯

  • 上面的 Case A/B/C 處理的是「規則 vs Agent」的比對

  • 這裡處理的是「同一個 Agent，但用不同視角」的多視角驗證

  • Agent A（嚴格派 — 採購方視角）：最壞情況，寧可多疑

  • Agent B（平衡派 — 業界慣例視角）：台灣常見做法，折衝考量

  • 結果：意見一致 → ✓ confirmed（兩個視角都認同，可信）

  • 結果：意見分歧 → ⚠️ pending（不同視角有分歧，法務需判斷）

  • 作用：多視角確認，避免單一視角的偏見，在不確定時誠實標記

Layer 3：法律依據錨定

  • 民法條文快取（真實查詢離線儲存）
  • 先例向量檢索（10 筆本地案例）
  • 協商建議能引用「民法第 216 條」
  • 作用：有根有據，不編造

Coverage Guard（橫向保護）

  • 字元層級驗證，防止無聲遺漏
  • 97% 安全閾值
  • 實測案例：v1 vs v4 原始文件 99.3%、修訂文件 98.9%，皆通過閾值
  • 作用：雙重保障

【為什麼這樣設計】

這個設計有三個關鍵特點，對應三個問題：

問題 1：「純規則看不完」

  • 解決：Layer 2 LLM 補漏 → 邊界案例也能抓

問題 2：「純 LLM 容易編造」

  • 解決：Layer 1 規則層 100% 確定 + Layer 1.5 多視角驗證 → 幻覺被隔離

問題 3：「法務信不過 AI 判斷」

  • 解決：✓ vs ⚠️ 清楚標籤 + Layer 3 法律依據 → 法務參與決策，不是盲信

這就是「既快又準又可信」的設計。

【準備】

【Step 1：上傳合約 — 30 秒】

場景：供應商送來新版合約，需要審查。我選 「範例模式」，選 v4（保護刪減版，最複雜的案例）。

【Step 2：風險旗標一覽 — 2 分鐘】

系統產出「完整風險旗標表」。看這個表：

  • 條款 ID
  • 風險等級（高/中/低）
  • 來源 ← 亮點 1（Case A/B/C 的結果）
  • MAS 狀態 ← 亮點 2（Agent A/B 的結果）
  • 風險類型
  • 觸發原因

亮點 1：「來源」欄 — Case A/B/C 去重複的結果

大部分風險標記了 ✓ 規則引擎。但找一個標記了 ⚠️ Agent 補漏的——就是這個：

「違約金改為千分之一」 風險等級：高 來源：⚠️ Agent 補漏（這是 Case C — 只有 Agent 發現） MAS 狀態：✓ confirmed（Agent A/B 都認同這是高風險） 風險類型：費率改動 觸發原因：「千分之一違約金，費率調降幅度不明確，存在風險」

為什麼來源是 ⚠️？ 因為：

  • 規則引擎看不懂「千分之一」這種中文寫法
  • LLM Agent 理解了「千分之一 = 0.3%」，比原來的千分之三下降了 66.7%
  • 所以這是 Case C：只有 Agent 發現
  • 法務看到 ⚠️ 標籤，知道要額外審視

亮點 2：「MAS 狀態」欄 — Agent A/B 多視角的結果

再看另一個條款，比如「責任上限改動」：

「責任上限從 100K → 50K」 來源：✓ 規則引擎（明確的規則判斷） MAS 狀態：✓ confirmed（Agent A 認為高風險，Agent B 也認為高風險，意見一致）

現在找一個 pending 的，表示 Agent A/B 分歧的：

「責任上限減小 + 保障加強」 來源：✓ 規則引擎 MAS 狀態：⚠️ pending（Agent A 認為高風險，Agent B 認為可接受，分歧需法務判斷）

為什麼是 pending？ 因為：

  • Agent A（嚴格派）：「責任上限減小了，這是高風險！」
  • Agent B（業界慣例派）：「雖然責任上限減小，但保障加強了，這在台灣業界常見，是可以接受的。」
  • 系統判斷：兩個視角有分歧，所以誠實地標 ⚠️ pending，法務自己判斷

總結：

  • ✓ 規則引擎 = 確定性高，已驗證
  • ⚠️ Agent 補漏 = 邊界案例，需確認
  • ✓ confirmed = A/B 一致，可信
  • ⚠️ pending = A/B 分歧，需判斷

這就是「規則 + AI 補漏 + 多視角驗證」的完整效果。

【Step 3：協商建議 — 2 分鐘】

現在點選這個「千分之一」條款，展開協商建議。

系統給出三層方案：

🟢 Tier 1（首選立場）

  • 我們的建議：違約金不應該有年度調整空間，建議改回千分之三
  • 民法依據：民法第 216 條（損害賠償的合理性）
  • 建議條文修改：[具體文字]

🟡 Tier 2（可接受的折衝）

  • 如果對方死守千分之一，我們可以接受，但要求加 Cap：年調幅度不超過 3%
  • 業界慣例參考：[資料]

🔴 Redline（絕不退讓的底線）

  • 絕對不能接受：年調幅度超過 5%

這樣，法務就可以進談判了。

  • 如果對方願意回到千分之三，最好
  • 如果對方不願意，「好，那我們接受千分之一，但你要給我 Cap @ 3%」
  • 如果對方連 3% 都不願意，「對不起，這超過我們的 redline，簽不了」

一份報告，三層決策依據。 法務可以帶著這份報告去談判，不用臨時想辦法。

Q&A 備援彈藥

【若被問「怎麼保證不遺漏？」】

答：我們用 Coverage Guard——字元層級的文字守恆檢查。

50 頁合約，解析前後字元數不一致 > 3%，系統自動警示。

實測案例：v1 vs v4 原始文件 99.3%、修訂文件 98.9%，皆通過 97% 閾值。

加上高風險 5/5 全發現（100% recall），雙重保障。

【若被問「為什麼只讀變動段落？」】

答：我們實驗過：讀全文 vs 只讀變動段落。

結果：只讀變動段落精準度更高、成本降 30%、避免 LLM 被無關細節干擾。

這是經過測試的工程決定，不是技術限制。

【若被問「多 Agent 怎麼工作？」】

答：Agent A（嚴格派）和 Agent B（平衡派）獨立分析同一條款。

意見一致 → ✓ confirmed 意見不一致 → ⚠️ pending（法務判斷）

重點是：我們不是讓 AI 投票表決，而是展現分歧，給法務更完整的資訊。

【若被問「Layer 3 怎麼實現？」】

答：我們接了真實民法資料庫 + 向量檢索。

協商建議會引用真實法條，比如「民法第 216 條」。

法務看到建議時，直接看到法律依據，不是憑空的。
