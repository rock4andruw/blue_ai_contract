## 依 Pipeline 順序詳解

> 每一步都附「技術棧」（快速對照表）+「怎麼運作」（部長追問「你這個差異是怎麼做到的、怎麼處理的」時，能直接照這段白話講，全部依實際程式碼查證，不是簡化過的示意）。

### Step 1：文件解析（`parser.py`）

| 檔案格式 | 套件 |
|---|---|
| PDF | `pdfplumber` |
| DOCX | `python-docx`（含表格與段落依原始順序交錯解析） |
| Markdown | 自建 Regex 條款切分器（支援「第 N 條」「N.N」「一、二、三」「Article N」等格式） |

**怎麼運作**：目標是把一份合約檔案，切成一條一條獨立的「條款」，每條都有自己的編號、標題、內文，這樣後面才能一條一條比對。

- **Word 追蹤修訂要先清乾淨**：合約如果是用 Word「追蹤修訂」編輯過再存成文字，裡面會夾雜 `<del>被刪除的字</del>`、`<ins>新增的字</ins>` 這種標記。系統會先把 `<del>` 整段拿掉（因為那是已經被刪除、不該存在的內容）、把 `<ins>` 的標記拿掉但保留裡面的文字（因為那是已經被接受的新增內容），確保後面比對的是「乾淨的最終文字」，不是帶著修訂痕跡的原始檔案。
- **Markdown 用「先切大段、再切小段」兩層邏輯**：先用 `## 標題` 把整份文件切成大段（通常對應到「第 N 條」這種大條款），每一大段裡面如果還有 `4.1`、`4.2` 這種編號子項目，再往下切成更細的子條款。這樣像「第 4 條 服務水準」底下的 `4.1 可用率標準`、`4.2 例外情況` 會被拆成兩個獨立的比對單位，不會被當成同一大塊文字比對，比對精準度才夠細。
- **文件最前面的標題（例如「SLA 合約 v4」）不會被當成條款去比**：因為版本標籤只是檔名層級的資訊，不是雙方要談判的合約內容，如果把它也當條款比對，會出現「這條有改」的假警報（其實只是版本號從 v1 變 v4，內容根本沒動）。
- **PDF**：用 `pdfplumber` 把每一頁的文字抽出來，串成一整份文字後，用「遇到空行就切一段」的方式切成條款——這是比較粗略的作法，適合排版單純的合約，遇到雙欄排版的複雜 PDF 目前還沒特別處理（已知限制，記錄在待辦清單）。
- **DOCX 最容易踩的坑，已經修過**：Word 文件裡的表格（例如付款排程表）跟段落文字，在 python-docx 這個套件裡預設是分開兩份清單存放，如果照預設寫法讀，會**整個表格內容消失不見**、系統完全不知道它存在過。現在的做法是直接照 Word 檔案原始的 XML 結構逐一讀取，段落跟表格出現的順序完全照原文排列，表格會被轉成「儲存格用 `|` 分隔的文字列」，跟其他段落用同一套邏輯切成條款——確保簽名欄、費率表這類容易藏在表格裡的重要內容不會被漏掉。
- **每條條款會算一個指紋（MD5 雜湊）**：把條款內容的空白去掉、轉小寫後算雜湊值。這個指紋在下一步（結構對齊）扮演關鍵角色——兩條指紋完全一樣，代表這條完全沒被改過，可以直接跳過，不用浪費力氣去比對它。

### Step 2：結構對齊（`alignment.py`）

- **LCS**：`difflib.SequenceMatcher`（Python 標準庫）
- **Needleman-Wunsch**：自實作動態規劃演算法（`gap_penalty=-0.42`, `similarity_threshold=0.28`）
- 三階段比對：exact hash → clause number → DP alignment
- 學術依據：arXiv 2604.19770（Hybrid Multi-Phase Page Matching）

**怎麼運作**：這一步要解決的問題是——舊版第 5 條，在新版裡可能變成第 6 條（前面被加了一條），甚至內容一模一樣但位置換了。**如果只是「第幾條對第幾條」死板比對，位置一換就整個對不上、產生一堆假警報。** 系統用三層由嚴到鬆的邏輯，逐層去比對「舊版這條」對應「新版哪一條」：

1. **第一層：指紋完全比對**——直接拿 Step 1 算好的 MD5 指紋，去比舊版跟新版的條款清單。指紋一樣的，代表這條文字完全沒變，直接標記「相同」跳過；指紋序列不連續、明顯對不上的段落，才進入下一層細比。這一層很快，因為大多數條款其實沒有變動，能先過濾掉。
2. **第二層：靠「條號」或「標題」抓對應關係**——對於指紋比不出來的段落，先看有沒有相同的條款編號（例如兩邊都有「第 11.1 條」），有的話直接配對，信心度算 90%；沒有編號的，改看標題文字是不是完全一樣，信心度算 80%。這一層處理的是「內容改了，但這一條還是這一條」的情況。
3. **第三層：Needleman-Wunsch 動態規劃**（生物資訊學拿來比對 DNA 序列的演算法，這裡拿來比合約條款）——前兩層都配對不到的，才動用這個。做法是：把剩下沒配對到的舊條款和新條款排成一個表格，每一格算「這條舊條款」跟「這條新條款」的文字相似度（0 到 1 分），再用動態規劃找出一條「總分數最高」的配對路徑——這條路徑可能是「配對」（兩條夠像，當作是同一條被改過）、也可能是「跳過」（這條在新版被刪掉了，或這是新版新加的）。跳過會扣分（懲罰值 -0.42），逼演算法優先選相似度夠高的配對，不要亂跳。**如果算出來的相似度連 0.28 都不到**，代表兩條根本是不同的東西，系統會誠實地把它處理成「舊的被刪除、新的是新增」，不會硬凹成同一條被改過。

**具體例子**：舊版「第 12.5 條」在新版被重新編號成「第 12.6 條」，但內容幾乎沒變——前兩層（指紋、條號）都配不上（指紋因為條號文字也算進內容而不同、條號本身也不同），會落到第三層，靠文字相似度算出這兩條其實內容 95% 像，判定為「同一條被改了編號」，而不是誤判成「刪掉一條、又新增一條」。

### Step 3：差異計算 + Coverage Guard（`diff_engine.py`）

- 純字元層級比對，無外部套件
- Coverage Guard：字元計數比對（parsed vs raw text），97% 閾值

**怎麼運作**：這一步把 Step 2 算出來的「哪條配哪條」關係，轉換成「這條到底是新增、刪除、還是被改了內容」這種明確分類，供後面的風險判斷使用。

- **三種分類**：舊版跟新版都有、但指紋不同 → 「修改」；只有舊版有 → 「刪除」；只有新版有 → 「新增」。指紋完全相同的，直接略過，不會產生一筆差異紀錄（沒改的東西不用浪費資源分析）。
- **條款編號重排的補救機制**：Needleman-Wunsch 有時會把「同一條被重新編號」誤判成「刪除一條 + 新增一條」兩筆獨立紀錄（因為條號不同、相似度算法在極端情況下沒抓到）。系統會在最後做一次補救：把所有「被刪除」跟「被新增」的條款兩兩比對文字相似度，只要有一對相似度 ≥ 75%，就合併回「修改」這一類，條款編號會標成「12.5→12.6」這種格式，讓法務一眼看出是編號變了、不是內容真的整條換掉。
- **文字守恆檢查（Coverage Guard）**：這是一個獨立於上面差異分析之外的**額外保險機制**。做法是：把原始合約的完整文字，跟系統實際解析出來、放進條款清單裡的文字，各自做「標準化」處理（去掉標點符號、統一空白、拿掉格式標記，只留下真正有意義的文字），然後**比較兩邊的字數**。如果解析後的文字字數少於原文的 97%，代表**有一部分內容在解析過程中不見了，但系統自己不知道**——這時候會觸發警示，並且用文字比對工具具體標出「大概是哪一段不見了」的線索（前 50 個字），提示人工去原始檔案複核。**這個機制保護的是「系統解析錯誤導致內容憑空消失」這個風險，不保證條款配對關係一定正確**——兩者是分開的兩道防線。

### Step 4：Risk Rule Engine（`risk_engine.py`，Layer 1）

- 純 Python + `re`（Regex），14 條硬編碼規則
- 中文數字/分數解析器自實作（`千分之X`／`百分之X`／`萬分之X` → 標準化百分比）
- 不依賴任何 LLM，判斷 100% 確定性

**怎麼運作**：這一步把 Step 3 產出的每一筆「差異」，拿去跟 14 條寫死的規則逐一比對，判斷這筆差異算不算風險、風險多高。**這一整層完全不呼叫 AI，是純粹的條件判斷式邏輯**——這是刻意的設計，因為規則判斷的東西必須 100% 可預測、可解釋，不能有 AI 的隨機性。

每條規則的判斷邏輯大致是同一個套路（以「責任上限」規則為例具體說明）：

1. **先看關鍵字**：這筆差異的文字裡有沒有出現「上限」「不得超過」這類跟責任上限有關的詞？沒有的話這條規則直接跳過，交給別的規則或 Agent 處理。
2. **從文字裡把「數字」抽出來**：合約裡數字有很多種寫法——「12 個月」「十二個月」「0.3%」「千分之三」——規則用一組 Regex（正規表示式）去抓阿拉伯數字寫法，抓不到的話再用備援邏輯試著把「十二」「千分之三」這種中文數字/分數轉換成標準數值（例如「千分之三」換算成 0.3%）。
3. **比較新舊數字**：新的數字如果比舊的差（例如賠償基礎從「過去 12 個月」縮成「過去 6 個月」），就判定為風險；如果數字沒變或變得更有利，就不觸發。
4. **輸出結構化結果**：不是只丟一句「有風險」，而是明確寫出風險代碼（例如 `RISK_LIABILITY_CAP_CHANGED`）、風險等級（高/中/低，這個等級也是規則本身決定的，不是 AI 判斷的）、還有一句話講清楚「為什麼」（例如「賠償計算基礎由 12 個月縮短為 6 個月」）。

**這套設計對部長的意義**：因為完全是條件判斷，同一份合約重跑一百次，一定得到一模一樣的結果——這是「高風險 100% 不漏判」這個承諾的技術基礎，AI 有隨機性做不到這種保證，所以確定性的部分刻意不交給 AI。

**2026-07-09 修復**：`_extract_years()`（NDA 保密期規則 `rule_confidentiality_weakened` 用）原本只認阿拉伯數字「5年」，中文數字「五年→二年」這種台灣合約常見寫法完全抓不到、規則靜默漏判——這個規則從寫出來到發現前**從未被任何真實或測試資料驗證過**。已用合成測試案例重現 bug 並修復（複用同檔案已有的 `_cn_num_to_int()` helper），fail-then-pass 驗證通過，`evaluate.py` 回歸測試 `high_recall=100%` 無退化。測試腳本：`scratchpad/test_nda_confidentiality_rule.py`（未進 repo）。

### Step 5：Verification Agent（`verifier.py`，Layer 2）

- 主要模型：`gemini-3.1-flash-lite`
- 備援模型：`claude-haiku-4-5`
- 語意補漏，只讀變動段落（不讀全文）
- 交叉核對 key：`(clause_id, 風險類別)`

**怎麼運作**：Step 4 的規則引擎再嚴謹，也是「寫死的條件判斷」，一定會有沒想到、沒寫進規則裡的變化方式（例如合約用了規則沒預期到的措辭）。這一步用 LLM 的語意理解能力去補這個洞。

1. **只餵「有變動的部分」，不是整份合約**：把 Step 3 篩出來的所有差異（新增、刪除、修改的段落）組成一份摘要，一次性送給 LLM，不會把沒改過的內容也送進去——這樣做的好處是省成本（token 少很多）、也讓 LLM 專注在真正有變化的地方判斷，不會被無關的條款內容干擾判斷。
2. **要求 LLM 輸出結構化的風險清單**：不是讓 LLM 自由發揮寫一段分析，而是要求它針對每個它認為有問題的條款，輸出「條款編號、風險等級、為什麼有風險、原文佐證」這種固定格式的資料，方便後續程式處理。
3. **交叉核對，決定要不要保留 Agent 的發現**——這是整個系統裡最關鍵的一段邏輯，直接對應「來源」欄位的判斷：
   - 系統先建立一個「規則引擎已經涵蓋了哪些條款、哪些風險類型」的清單（用「條款編號 + 風險類別」當作識別碼，不是只看條款編號——因為同一條款可能同時有兩種不同性質的風險，例如「責任上限」跟「違約金費率」）
   - Agent 找到的每一個發現，去比對這個識別碼有沒有已經在規則引擎的清單裡：**已經有了** → 代表規則跟 Agent 找到同一件事，保留規則引擎的版本就好（規則的判斷已經 100% 確定，不需要 Agent 再講一次）；**沒有** → 代表這是規則引擎完全沒發現的新東西（可能是全新的條款、也可能是同一條款裡規則沒抓到的另一種風險），這時候才會被加進最終報告，並且清楚標記「⚠ Agent 補漏」，讓法務知道這筆判斷是 AI 語意理解找到的，跟規則引擎百分之百確定的判斷不是同一個信任等級。
   - 這種「同時被補漏」的發現，還會額外記一筆到候選規則清單（`candidate_rules.jsonl`），如果同一種模式在多份合約裡重複出現，就是規則引擎該擴充新規則的訊號——這是系統會隨著使用累積、自己變聰明的機制，但不是自動生成規則，是留給人工複核決定要不要正式寫成新規則。

### Step 6：LLM 摘要生成（`llm_service.py`）

- 主要模型：`gemini-3.1-flash-lite`
- 備援模型：`claude-sonnet-4-6`
- 無 API key 時：Template Fallback（純規則化文字模板，不呼叫任何 LLM）

**怎麼運作**：Step 4/5 判斷出來的風險，內容還是很「工程師/法律用語」（例如 `RISK_LIABILITY_CAP_CHANGED`、觸發原因是條件式的一句話）。這一步把它翻譯成非法律背景的人也看得懂的白話文字。

1. **先查有沒有真實依據可以引用**（銜接 Step 7）：在生成文字之前，系統會先去查這個風險類型有沒有對應的真實法條、有沒有過去審查過的相似案例。
2. **把「風險判斷 + 法條 + 先例」一起丟給 LLM**，要求它輸出四個固定欄位：白話說明（一句話講清楚發生了什麼事）、商業影響（對公司實際運營的影響）、2-3 個協商對策、法律依據（**只有真的查到依據才填，查不到就留空字串，不准 LLM 自己編一個法條號碼**——這條規則寫在 prompt 裡明確要求）。
3. **三層備援**：有 Gemini key 就用 Gemini，沒有就試 Claude，兩個都沒有（例如 demo 環境沒設定 API key）就用純 Python 寫死的文字模板頂上——保證系統在完全沒有 AI 可用的極端情況下，還是能產出一份看起來完整的報告，只是內容比較制式，不是根據這份合約量身生成的。

### Step 6.5：MAS 雙代理人驗證（`mas_service.py`，Layer 1.5，僅高風險項目）

**怎麼運作**：只有被判定為「高風險」的條款才會走這一步（成本考量，中低風險不需要這麼重的驗證）。目的是讓兩個不同立場的「審查員」各自獨立判斷同一個風險，如果兩邊看法一致，代表這個判斷很可靠；如果兩邊看法差很多，誠實告訴法務「這裡有分歧、需要你自己判斷」，不硬給一個答案。

1. **兩個角色平行審查**：系統同時開兩條執行緒，把同一個風險條款分別送給「嚴格派」（扮演極度保守的甲方法律顧問，原則是寧可高估風險也不要漏掉）跟「平衡派」（扮演促成交易的商務顧問，會參考業界慣例判斷這是不是合理範圍內的條款）。兩者用同一顆模型（見下方現況說明），差別只在於給的角色設定（system prompt）不同，靠角色扮演製造出不同的判斷視角。
2. **兩邊各自回傳一個等級判斷**（高/中/低）+一句話說明理由，彼此看不到對方的答案（盲評設計，避免其中一方受到另一方意見影響而改變判斷，這是刻意仿照學術上「避免評審互相影響」的作法）。
3. **Judge 邏輯合併兩邊的結果**：
   - **兩邊給的等級完全一樣** → 標記「✓ confirmed（雙重驗證）」，採用這個一致的等級
   - **兩邊差一級**（例如一個說高、一個說中） → 還是算「confirmed」，但採用比較嚴格的那個等級（寧可謹慎，不要因為平衡派覺得還好就降低警示）
   - **兩邊差兩級**（一個說高、一個說低，代表真正的重大分歧） → 標記「⚠ pending（待確認）」，維持原本規則引擎判斷的等級，不採用任何一邊的意見，明確告訴法務「AI 內部對這件事看法不一，需要你自己判斷」

**現況（資源限制下的暫行設計）**：Agent A（嚴格派）+ Agent B（平衡派）目前共用同一組模型優先序（有 `GEMINI_API_KEY` 時兩者皆用 `gemini-3.1-flash-lite`；只有沒有 Gemini key 時才 fallback 為 `claude-haiku-4-5-20251001`），靠不同 system prompt（persona）製造視角差異，非同時使用兩種模型（見 `_call_agent()`／`run_mas()` 邏輯，A/B 傳入同一組 key）。平行執行機制：`concurrent.futures.ThreadPoolExecutor`。知識庫來源：`.claude/skills/contract-risk-analysis.md`（Agent A）、`.claude/skills/negotiation-strategy.md`（Agent B），執行時動態載入。

**設計目標（Phase 2，異質模型）**：改為 Agent A 用 Gemini、Agent B 用 Claude 真正同時運作，兩個不同供應商互相 cover，避免同一 API／模型自我一致性偏誤（self-enhancement bias）。有文獻佐證：*Can LLM Agents Really Debate?*（同質 Agent 辯論易形成 Echo Chamber，強化錯誤而非修正）、*Justice or Prejudice? Quantifying Biases in LLM-as-a-Judge*（同模型系列互評存在 self-enhancement bias，多模型取平均更可靠）——現況受限於資源，先用同一供應商（Gemini）驗證盲評設計本身是否有效，異質模型是下一步。

### Step 7：Layer 3 法律依據錨定

- **MCP**：`mcp-taiwan-legal-db`（台灣法規 MCP Server）
  - **現況**：只用 `query_regulation`（查法條文字）這個工具，**離線建置一次**，結果存成 `legal_citations_cache.json`，Demo 執行期同步讀本地檔案，**不即時連網呼叫 MCP**——刻意設計，避免 Demo 現場網路依賴風險
  - **Phase 2 規劃**：改用 `search_judgments`（即時判決查詢，查法院實際怎麼判，不只是法條文字），從離線快取升級成即時查詢，前提是系統穩定性不再受限於單次 Demo
- **先例檢索**：本地 JSON 語料（`precedent_corpus.json`）+ Gemini Embedding（`gemini-embedding-2`，3072 維）+ 本地 cosine similarity 計算，無向量資料庫（pgvector 為 Phase 2 規劃）

**怎麼運作**：這一步的目標是讓協商建議「有憑有據」，不是 LLM 憑空講一句「建議修改」。分成兩條獨立的查證路徑：

1. **法條查詢，靠字典直接查表，不是語意搜尋**：系統每個風險類型（`RISK_LIABILITY_CAP_CHANGED` 這類代碼）都有預先建立好的對照表，告訴系統這個風險類型該引用哪一條民法。查詢的動作就是拿風險代碼去查這張表，是精確比對，不是模糊的 AI 猜測。**這張表是離線建置好的**——事先用 MCP 工具查過一次法規資料庫，把查到的真實條文內容存成本地 JSON 檔案，正式跑 Demo 的時候只是讀這個本地檔案，完全不連網——這是刻意設計，避免現場網路不穩導致查不到法條。如果是 Agent 補漏找到的風險（沒有明確的風險代碼可以查表），系統會先用跟 Verification Agent 同一套分類邏輯，猜這個發現屬於哪個風險類別，再用類別去找有沒有同類別的法條可以借用。
2. **先例檢索，靠真正的向量語意相似度，不是關鍵字比對**：系統把要查詢的文字（風險的觸發原因說明）送去 Gemini 的 Embedding API，轉換成一個 3072 維的數字向量（可以想成是把這段文字的「語意」壓縮成一組座標）。本地語料庫裡的每一個過去案例，也都事先算好了各自的向量。系統把查詢向量拿去跟語料庫裡每一個案例的向量做「餘弦相似度」計算（一種衡量兩個向量方向像不像的數學方法，分數 0 到 1，越接近 1 代表語意越相近），找出分數最高的那一筆。**如果最高分都低於 0.5，系統會誠實回報「沒有找到相似先例」，不會硬塞一個關聯性很低的案例充數**——寧可承認查無資料，也不要給誤導性的參考。
3. **最後交給 LLM 統整成一句話**（在 Step 6），但**規則很嚴格**：LLM 只能引用系統實際查到的法條原文和先例內容，絕對不能自己發明法條號碼——這條限制寫死在 Step 6 的 system prompt 裡，是防止 LLM「幻覺」編造法律依據的關鍵防線。

### Step 8：協商對策生成（`negotiate_service.py`）

- 主要模型：`gemini-3.1-flash-lite`
- 備援模型：`claude-sonnet-4-6`
- 三層 Playbook（Tier 1／Tier 2／Redline）+ 批次協商矩陣

**怎麼運作**：這一步是按需觸發的（法務點了「生成對策」按鈕才會執行，不是每次比對都自動跑，節省成本），目標是產出「首選立場 / 可接受折衷 / 絕對底線」三層談判策略，而不是只給一個模糊的建議。

1. **先查有沒有預先寫好的標準立場**：系統對每一種風險類型，都有法務同仁事先寫好、存在知識庫檔案裡的標準協商立場（例如「責任上限被縮小時，首選立場是要求恢復原本的計算基礎」）——這是靜態內容，不需要每次都重新生成，速度快、且保證措辭穩定符合公司一貫立場。
2. **有 AI 可用時，再用 LLM 依實際條款文字微調**：把預先寫好的標準立場當作範例基礎，連同這次真正的條款原文（新舊版本文字）一起送給 LLM，要求它產出貼合這份合約實際措辭的版本——例如標準立場範例寫的是通用情境，但這份合約的責任上限具體數字是多少、寫法是什麼，LLM 會依照實際文字調整用詞，讓建議可以直接複製貼上進合約，而不是要法務自己再改寫一次。
3. **輸出固定結構**：Tier 1（首選，附具體可貼入合約的替換條文）、Tier 2（可接受的折衷方案，不需要每次都上呈法務主管）、Redline（絕對底線，低於這條就要升級處理）。
4. **協商矩陣是批次版**：一次把所有高風險條款都跑過這個流程，組成一張「條款/對方訴求/我方立場/折衷方案/底線」的對照表，可以直接列印帶去談判現場。

### Step 9：報告組裝（`report_generator.py`）

- 純 Python 字串組裝，輸出 Markdown

**怎麼運作**：把前面所有步驟產出的結構化資料（風險清單、白話摘要、協商建議、法律依據、Coverage Guard 結果），組裝成一份完整的 Markdown 報告文字。**這一步完全不呼叫任何 LLM，是純粹的資料組裝與排版**——這是刻意的架構選擇：前面的步驟已經用 AI 生成過內容一次了（Step 6 的白話摘要），如果最後組報告這一步又讓 AI 重寫一次，等於多一次「AI 可能把正確的數字或文字改錯」的風險，卻沒有帶來任何好處。實際測試過讓 AI 直接生成完整報告（拿真實 v4 案例資料對照測試），結果 AI 版本在測試中把總條款數量算錯、還憑空生出一個不存在的比對日期——證實了「內容由 AI 負責、組裝排版由確定性程式碼負責」這個分工設計是正確的，細節見下方「死資產」章節的實測記錄。整體評估的高中低風險等級判斷、必須協商/建議協商/可接受的分類，也都是根據數量做簡單的條件判斷，不是 AI 決定的。
