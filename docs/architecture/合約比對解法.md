# 合約文件比對——解法文件

> 本文件說明本專案對「合約文件比對」問題的完整解法：問題拆解、每一步的設計與理由、背後的設計原則，以及與現行實作的對應。
> 適用讀者：團隊成員、評審答辯準備、未來接手的開發者。
> 撰寫：2026-07-03｜狀態：與現行實作同步（含三項已識別、尚未實作的缺口，優先級不同，見第五節）

## 一、問題拆解：比對是四個問題，不是一個

「合約比對」聽起來是一個功能，實際上是四個本質不同的子問題，各自需要不同性質的解法：

| # | 子問題 | 本質 | 失敗的代價 |
|---|--------|------|-----------|
| 1 | **保真解析** | 把文件變成條款序列，一個字都不能丟 | 上游丟了內容，下游再聰明都是零 |
| 2 | **條款對齊** | 舊版第 N 條對應新版哪一條（可能改號、改寫、拆併） | 配對錯了，後續判斷全部建立在錯的前提上 |
| 3 | **變更判定** | 對齊後的每一對：變了什麼、有沒有風險 | 漏判高風險 = 法務工具失去存在意義 |
| 4 | **可信輸出** | 每個結論都能回答「你憑什麼這樣說」 | 無法追溯來源的結論，法務不敢用 |

**關鍵認知**：大多數方案把力氣全花在第 3 步（選模型、調 prompt），但實務上致命的是第 1、2 步。本專案的真實開發歷程驗證了這件事——曾發現 138 段無條號條款被靜默丟棄、DOCX 原生表格內容完全沒被讀入。這兩個 bug 都不是「判斷不準」，是「根本沒看到」，且下游任何智能層都無法補救。

## 二、每一步的解法

### 第 1 步：保真解析 + 文字守恆檢查

**解析器選擇是次要問題**。`pdfplumber` + `python-docx` 經三組真實公司合約實測足夠（DOCX 需依文件原始順序交錯讀取段落與表格，見 `parser.py` 的 `_iter_docx_block_items`）。不引入 Docling / MarkItDown 等新依賴，除非遇到已證實解不了的真實案例（目前已知未驗證的邊界：雙欄排版 PDF）。

**關鍵設計是「文字守恆律」（coverage guard，規劃中）**：

- 解析後：所有條款字元總量 ≈ 原始文件字元量
- Diff 後：所有 diff 項（含 unchanged）字元總量 ≈ 兩份解析結果字元量
- 缺口超過閾值（容忍空白/格式差 2-3%）→ 掛 `COVERAGE_GAP` 警示，附缺口位置供人工複核

這是整個系統唯一能做到「數學上保證沒有內容被靜默漏看」的機制。純字元計數，不需要 LLM，成本趨近於零。它不保證「配對關係正確」，只保證「沒有東西整段消失」——但後者正是實際踩過兩次的失敗模式。

### 第 2 步：分層對齊，語意檢索只處理殘餘

對齊策略按成本由低到高分層，前一層解決不了的才進下一層：

1. **條款號錨定**：條款號相同 → 直接配對（零成本，解決多數情況）
2. **內容相似度**：條款號不同 → LCS + Needleman-Wunsch + difflib 相似度後處理（≥75% 視為重新編號的同一條款）——現行實作，見 `alignment.py`
3. **語意殘餘配對（規劃中，待根因分析證明需要）**：前兩層都失敗的殘餘條款，才動用 embedding 語意配對

**成本邏輯**：一份 200 條的合約通常 95% 條款能被前兩層便宜解決，剩 5-10 條才值得付 embedding 的成本。全量上語意對齊（如 SBERT + 匈牙利演算法）是把 95% 不需要語意的配對也付了語意的價格——這是我們評估外部提案後不採納全量語意對齊的理由。

### 第 3 步：確定性判斷打底，LLM 只補語意殘餘

兩層判斷，輸入視角刻意不同：

| 層 | 機制 | 負責 | 保證 |
|---|------|------|------|
| Layer 1 | 規則引擎（15 條規則，pure Python） | 可枚舉的風險模式（違約金比例、賠償上限等有明確數字特徵者） | 預定義類別 100% 召回、可重現、零成本 |
| Layer 2 | Verification Agent（LLM） | 規則看不懂的語意變化（中文分數「千分之一」、換句話說的弱化） | 語意泛化，經 (clause_id, 風險類別) 交叉核對去重 |

**LLM 只讀變動條款、不讀全文**（`verifier.py` 的 `_build_diff_prompt` 過濾 `change_type != "unchanged"`）。理由有二：

1. **成本**：實測合成範例兩版合計約 1,000-3,600 tokens；真實合約（166-242 條款）外推 1.8-3.5 萬 tokens。全文讀取模式在真實合約規模下是 10 倍以上的成本差，且每次比對都要重付一次。
2. **聚焦**：給 LLM 的問題越窄，幻覺空間越小。「這個變動有沒有風險」比「整份合約哪裡有問題」可靠得多。

**代價與兜底**：LLM 救不了上游漏掉的東西（沒進 diffs 的內容它根本看不到）——所以需要第 1 步的守恆檢查封住這個缺口。**兩者是一組的設計，不是獨立的兩個功能。**

判斷之後的第三層驗證：MAS 雙重驗證（Agent A 嚴格 / Agent B 平衡，Judge 矩陣合議），只跑高風險旗標（成本控制），分歧時標 `⚠ 待確認` 交人工。

### 第 4 步：來源可追溯

- 每個風險旗標標明來源：`✓ 規則引擎` / `⚠ Agent 補漏`（`source` 欄位）
- 法條引用只能來自檢索到的原文（`legal_citations_cache.json`，mcp-taiwan-legal-db 離線查回的真實條文）；檢索不到就留空，不准 LLM 生成——空白 = 誠實揭露沒有依據
- 原始檢索資料與 LLM 轉述分開呈現：UI 的「⚖ 法律依據」（LLM 統整句）之下另有「🔎 Layer 3 原始檢索資料」（🏛 MCP 法條原文框 / 📚 向量先例框，含相似度百分比），評審與法務可自行核對 LLM 有沒有轉述失真

**原則**：法務工具的本質是信任工具——「我不知道」比「我猜一個」值錢。

## 三、背後的三條設計原則

1. **確定性能解決的，不用機率解決**。「變沒變」是文字問題，用演算法；「有沒有風險」才分層交給規則 + LLM。把簡單問題升級成機率問題不是更聰明，是把零成本、100% 一致的判斷降級成要花錢、可能不穩的判斷。

2. **每一層 LLM 的引入，都要同時回答「它漏了誰來接」**。LLM 補規則引擎的漏（語意層）；守恆檢查補 LLM 上游的漏（結構層）。沒有兜底機制的智能層是裸奔。

3. **成本花在殘餘上**。全量便宜掃描 + 殘餘精細處理。這個模式在系統中已驗證的兩處實作重複出現：判定（LLM 只讀變動條款，不重讀全文）、MAS（只驗證高風險旗標，中低風險不驗證）——不是巧合，是同一條原則的兩次應用。對齊層的語意殘餘配對（見第五節缺口 #2）是同一條原則的第三個候選應用場景，但**尚未實作**，不算已驗證的例子。

## 五、已識別、尚未實作的缺口（誠實記錄）

| # | 缺口 | 優先級 | 前置條件 |
|---|------|--------|---------|
| 1 | **文字守恆檢查（coverage guard）** | 高——賽前唯一建議動手的架構補強 | 無，可直接做（純字元計數，半天內可實作+測試） |
| 2 | **語意殘餘配對（對齊第 3 層）** | 低——先查根因再決定 | 需先用 38 筆 gold set 分析 Overall Detection 67% 的缺口是「配對錯」還是「配對對了但規則沒判出」；若是後者，做語意對齊完全不會改善數字 |
| 3 | 雙欄排版 PDF 解析 | 路線圖 | 遇到真實案例再評估（候選：IBM Docling） |

**第 2 項的方法論備註**：不要先選武器再找戰場。任何演算法升級之前，先用既有 gold set 做 miss 的根因分類——這是本專案一貫的做事方式（先測試、先找根因、再動手）。

## 六、一句話總結（答辯用）

> 「合約比對的難點不在比對演算法，在**保證系統看過每一個字**、**配對不錯**、**判斷可信**。我們已實作的每一層——分層對齊、規則引擎、Verification Agent、來源可追溯——都對應一個真的用三組真實公司合約踩過的坑，不是紙上架構；文字守恆檢查是我們從這些坑裡歸納出的下一步補強，目前還在規劃階段，尚未實作。」

**若被追問「所以守恆檢查做了沒」**：誠實回答「還沒做，這是我們自己發現的架構缺口，判斷是賽前優先度最高的補強，理由是 XXX（見第五節）」——承認未完成，比含糊帶過更有說服力，這也是整份文件一貫的立場。
