## 一、Agent 優化：NLI 框架實驗 —— ✅ 已測試，結論：不採用

**2026-07-04 更新**：已完成 A/B 測試並還原，不需要再排入待辦。結果摘要：

- 測試法：備份 `verifier.py`，改成 NLI 三分類 prompt，用 v2-v6 五個範例跑一輪，跟改版前的基準線逐筆比對
- **結果是退步，不是改善**：
  1. v6 旗艦案例（「千分之一」費率）從 2 筆獨立發現被合併成 1 筆，`clause_id` 也從有意義的子標籤退化成純數字「3.1」
  2. v2 完全漏掉一筆基準線有抓到的 **high 風險**發現（P1/P2/P3 修復時效全面惡化）
  3. v5 同一條款（12.2）的 `risk_level` 從 high 被降成 medium，且漏掉另一筆基準線有的發現（12.3）
- 已依測試前訂好的判準（沒有明顯改善就不採用）**還原 `verifier.py` 至原版**，並重新驗證 v6 正確恢復兩筆獨立發現
- **結論**：這個方向已有明確反面證據，不建議之後再花時間重測同樣的 NLI 框架設計；除非未來有結構性不同的 prompt 設計（例如強制模型逐條款分開輸出，而非整批判斷），否則視為已排除的選項

### 是什麼

把 Verification Agent（Layer 2）的判斷框架，從現在的「開放式風險評估」（自由文字判斷風險等級與理由），改成學術上更收斂的 **NLI 三分類**（Natural Language Inference）：

- **蘊含（Entailment）**：修改後條款語意一致或對甲方更有利
- **矛盾（Contradiction）**：權利義務縮水、保障刪除 → 判定為不利變更
- **中立（Neutral）**：純字詞潤飾，無實質變更

### 為什麼考慮

這是查證外部技術提案時發現的、真正有新意的一點（不是撞名巧合，是提案裡唯一超出你們既有設計的部分）。NLI 是被學術驗證過的任務框架，決策邊界比「自由評估」窄，理論上能讓 LLM 判斷更一致、更少隨意發揮。

### 範圍與作法

- 只改 `verifier.py` 的 System Prompt 結構，不動 Rule Engine、不動資料流
- A/B 比較法：同一批真實合約 + 6 個 demo 範例，新舊 prompt 各跑一次，比對 Case A/B/C 判斷結果是否更一致（尤其是 trigger_reason 措辭穩定度、risk_level 判斷穩定度）
- 若新框架沒有明顯改善，直接不採用，不用勉強上版

## 二、未來願景：一個「記得歷史、有法源根據、懂商業判斷」的對話式法務助理

> 共同前提：以下能力都需要**真實資料或基礎設施**才有意義，賽前手上沒有這些條件，不建議搶做。硬做是表演，不是工程——這是這個 session 一路堅持的判斷準則。

### 好故事：把三個技術方向包裝成一個產品願景，而不是三條孤立的路線圖項目

原本 2.1（歷史合約庫）、2.2（MCP 判決查詢）、2.3（Insight 資本額分析）三項，各自看是三個獨立的技術升級，寫成路線圖條列容易讓人無感。**更好的講法**：這三項技術能力，其實是同一個產品願景的三個引擎——未來法務要問的不是「幫我跑一次分析」，是直接問一位「記得所有合約歷史、隨時查得到真實判決、懂得判斷對方公司財務體質」的法務顧問。三個技術方向剛好分別餵給這個助理三種「記憶」：

| 對話範例 | 需要的能力 |
|---|---|
| 法務：「這份新合約的違約金比例，我們接受得起嗎？」<br>助理：「這條有風險——比你們去年跟這家供應商簽的合約多讓了 2%。」 | 2.1 歷史合約庫（記得「這家供應商以前怎麼談」） |
| 法務：「有法源支持我們談判嗎？」<br>助理：「民法第252條規定違約金過高法院得酌減，我查了近三年類似案件，多數勝訴案例的違約金比例都在 5% 以上。」 | 2.2 MCP 即時判決查詢（不只查法條文字，查法院實際上怎麼判） |
| 法務：「這家供應商財務體質如何？這個罰款他們付得起嗎？」<br>助理：「這家公司實收資本額約 N 萬，這個 2000 萬的罰款上限可能超過清償能力，建議調整。」 | 2.3 Insight 資本額分析（懂得判斷合約條款背後的商業現實） |

**這個故事同時解答了「對話式介面要不要做」的問題**：對話介面不是額外加上去的功能，是這三個技術能力「被使用」的自然形式——資料庫是記憶、MCP 是法源、Insight 是商業判斷，三者湊在一起，最終使用者體驗理所當然是「用問的」，不是每次都重新跑一次批次分析。所以原本第三節「對話式介面」跟這一節本來就是同一件事，合併呈現。

**重要：故事講的是願景，範圍限定的原則不變**——對話介面仍然是「問答錨定在檢索到的資料上」（歷史合約庫查詢結果、MCP 判決查詢結果、Insight 分析結果），不是讓 LLM 自由發揮回答任何問題。見下方「對話式介面設計原則」。

### 2.1 真實歷史合約庫（PostgreSQL + pgvector）

**現況**：先例檢索用 10 筆手寫合成案例（緊扣 v2-v6 demo 模式），本地 JSON + cosine similarity，不架資料庫。

**未來版本**：文件/條款分兩層表（合約主表存 metadata：類型/管轄權/簽署方/狀態；條款明細表存文字+embedding），查詢時**先用 SQL 條件硬過濾**（例如只找台灣管轄、SLA 類型、有效合約）再做向量排序，避免語意相似但法律體系不同的誤配對。索引用 HNSW。（完整 schema 已在 `PROJECT_PLAN.md` 第九節「常見追問與回答」記錄過，可直接複用）

**前置條件**：需要真的持續累積的企業歷史合約庫。現在沒有這個資料來源——手上的客戶合約樣本是驗證 pipeline 用的測試資料，不是正式語料庫。

### 2.2 MCP 從離線建置升級成即時查詢，且用更有份量的工具

**現況**：`mcp-taiwan-legal-db` 只用了 `query_regulation`（查法條文字），離線建置成 `legal_citations_cache.json`，Demo 執行時同步讀本地檔案，不即時連網。

**未來版本**：這個套件其實還有 `search_judgments`（查真實法院判決，可用 `main_text` 關鍵字篩選勝敗訴結果）沒被用到。真實判決先例比單純法條引用更有說服力——法條是抽象規定，判決是「法院實際上怎麼判」，對協商立場的支撐力道更強。同時可以把「離線建置、同步讀檔」的架構限制解除，改成正式服務的即時查詢。

**前置條件**：目前刻意不在 Demo 執行路徑即時呼叫 MCP，是為了避免 Demo 現場網路依賴（可能斷線的風險點）。等系統不再受限於單次 Demo 的穩定性要求（正式上線、有維運團隊監控），這個限制才該解除。

### 2.3 Insight 分析（企業資本額比對罰款合理性）

**是什麼**：合約罰款條款變更時，自動查詢對方公司資本額，判斷罰款金額是否合理（已在 `PROJECT_PLAN.md`「中期展望」列過）。

**前置條件**：需要外部資料源（企業登記資料庫 API），不是合約文字本身能推導出來的，是資料庫/MCP 成熟後才解得開的功能。

### 2.4 對話式介面設計原則：問答錨定在檢索到的資料，不是自由對話

上面的對話範例是願景，實作時**範圍必須限定**：讓使用者針對「已產出報告 + 已檢索到的資料（歷史合約庫查詢結果、MCP 判決查詢結果、Insight 分析結果）」提問，而不是讓 agent 自由回答任何問題。

**為什麼要限定範圍**：整個系統的信任基礎建立在「確定性優先、LLM 只在窄範圍內解釋、沒有依據就留白」——如果對話介面變成「什麼都能問、agent 自由發揮」，等於把這套原則丟掉，回到「LLM 想講什麼就講什麼」的不可控狀態。限定成「錨定在檢索資料上的問答」，是把對話能力疊加在既有確定性核心之上，不是取代它——跟 Layer 3（法條/先例）的設計邏輯一致：新增能力，不犧牲既有信任保證。

**現在（沒有 2.1/2.2/2.3）就能支援的問題**：「為什麼這條被標高風險？」→ 直接引用該筆 `RiskFlag` 的 `trigger_reason` + 對應規則/Verification Agent 判斷依據，不重新生成新論述。這部分不需要等資料庫，隨時可做。

**✅ 已實作並測試（2026-07-04）**：`POST /api/v1/contracts/ask`（`llm_service.answer_report_question()`）——錨定在當次報告內容問答，實測 3 題含「引用風險理由」「引用法律依據」「超出範圍誠實拒答」皆正確。同時額外做了「協商矩陣」（`POST /api/v1/contracts/negotiate/matrix`，`negotiate_service.generate_matrix()`）——批次生成「對方訴求／我方政策／建議折衷方案／底線／法律依據」對照表，複用既有 `generate_playbook()`，實測 v4 全部 10 個高風險條款正常。兩者都是純組裝層，沒有新增判斷邏輯。**尚未接前端 UI。**
