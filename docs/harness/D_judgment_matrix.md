# D. 判斷力外化矩陣

> 目的：把高階模型的「直覺」變成弱模型可肉眼比對的 Checklist。
> 用法：卡住時，逐條對照下面的【正例／反例】，落在哪一欄就照那欄動作。**不要靠感覺，靠比對。**

---

## 1. 「方向錯了，立刻停下換路徑」的信號

出現以下**任一**信號，就**停止在原路徑上修修補補**，退一步重想或換做法（不是再改一次同一段碼）：

| # | 信號（可觀察） | 動作 |
|---|----------------|------|
| 1 | 同一個錯誤訊息**連續出現 2 次**，即使你改了東西 | 停。假設「我對問題的理解是錯的」，重讀需求/報錯，換診斷方向 |
| 2 | 為了讓 A 通過，你已經改了 3 個以上「本來不該動」的檔案 | 停。這是「錯誤前提」的味道，回頭質疑最初的設計選擇 |
| 3 | 你發現自己在「猜」API/函式簽名，而不是查到的 | 停。去讀原始碼/文件，別繼續堆猜測 |
| 4 | 修復讓測試從「1 個紅」變成「3 個紅」 | 停。你的修法引入了副作用，路徑錯了 |
| 5 | 你需要註解掉既有測試才能讓自己的碼「通過」 | 停。幾乎必錯，回報而非硬幹 |

**【完美正例】**：跑測試報 `KeyError: 'risk_level'`，改了取值方式仍同錯 → **停下**，重讀資料結構，發現上游根本沒產生該欄位 → 修上游。（對症）

**【典型反例】**：同樣 `KeyError`，第 1 次加 `try/except` 吞掉、第 2 次改預設值、第 3 次改成 `.get()`……錯誤換形狀但沒消失，**一路在下游硬補**。（原地打轉，違反信號 #1）

---

## 2. 「任務真正完成、可交付」的量化判準

**全部**滿足才算完成。少一條就是「部分完成」，如實回報，不得宣稱完成：

- [ ] **驗收條件逐條打勾**：派工時的每條 Rubric 都有「通過 + 一句證據」。
- [ ] **實際跑過**：不是「代碼看起來對」，而是真的執行過（測試綠 / demo 跑出預期輸出）。用了隔離驗證（[C](C_model_dispatch.md) §3），非自我背書。
- [ ] **無新增紅燈**：既有測試沒有因此變紅；`py_compile`/型別檢查通過。
- [ ] **範圍精準**：只動了該動的檔；沒有順手改無關的東西；未改動 `.claude/skills/` 的**格式或位置**（僅編輯 skill 檔的 prompt 文本內容是允許的，見 [skills_runtime_assets.md](skills_runtime_assets.md)）；未碰 `.env`、合約目錄。
- [ ] **可回溯**：改動點能用「檔案:行號 + 一句話」講清楚。

**【完美正例】**：「PR 目標＝修好 diff 空白處理。`pytest tests/test_diff.py` 5 綠（前 1 紅）；只改 `diff_service.py:88-95`；隔離 subagent read-back 確認邏輯；無其他檔變動。」→ 五條全勾，交付。

**【典型反例】**：「我實作完了，看起來應該可以。」→ 沒跑、沒證據、沒隔離驗證、範圍不明。**這不是完成，是猜測**。

---

## 3. 「觸發熔斷、停止自主、向 User 提問」的條件

出現以下**任一**，**立即停止自主作業**，把「現況 + 選項 + 你的建議」交給 User，等回覆：

| # | 熔斷條件 | 為什麼要停 |
|---|----------|-----------|
| 1 | 需要**不可逆或對外**的動作（刪檔、`git push`、發送、部署、動 production） | 越權風險，必須 User 授權 |
| 2 | 同一子任務**已升級到 Opus 仍連錯 2 輪** | 再試也是燒 token，換人類判斷 |
| 3 | 要**改動受保護資源的結構**（`.env`、合約目錄、`.claude/skills/` 的**格式或位置**、`src/` 的 4 處 loader）；註：僅編輯 skill 檔的 prompt 文本內容不在此列 | 高破壞性，需確認 |
| 4 | 需求**本身矛盾或缺關鍵資訊**，且無法從碼/文件推得 | 猜下去只會做錯方向 |
| 5 | 落到「**模糊的商業美感/品味決策**」（見 §4） | 弱模型注定失敗，別假裝 |
| 6 | Context window 即將耗盡 | 先收尾交接（見 [G](G_handover.md)），別半途爆掉 |

**【完美正例】**：發現要改的功能會影響 `git push` 到 main → **停**，回報：「此改動需 push 才生效，牽涉 main 分支，請確認是否授權，或我先開 feature 分支？」

**【典型反例】**：需求說「把報告改得更專業」，模型自己腦補了語氣、字型、配色一路改下去 → 這是 §4 的品味決策，**應熔斷卻沒停**。

---

## 4. 能力極限：品味/美感/商業判斷的應對標準（誠實條款）

**弱模型（甚至強模型）在「模糊的品味決策」上注定不穩**：例如「這段文案夠不夠打動評審」「這個 UI 配色高不高級」「這個提案語氣專不專業」。這些沒有客觀 Rubric，靠的是人類品味與商業直覺。

**遇到這類任務的具體應對標準（照做，不要自由發揮）**：

1. **不自行拍板**，也**不假裝有把握**。
2. **產出 2–3 個明確不同的候選**（例：三種標題語氣 / 三種版面），各自標明「取捨與適用情境」。
3. **觸發熔斷**（§3 條件 5），把候選交 User 選，附上你的**理由式建議**（「我傾向 B，因為對法務受眾更穩重」），但**決定權在 User**。
4. 若 User 已給過偏好（見專案記憶/回饋檔），優先套用其既定品味，而非重新發明。

> 一句話：**能量化的自己扛，不能量化的交出去。** 這是這套 Harness 的誠實邊界。
