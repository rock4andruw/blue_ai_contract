# F. 知識迭代與反思協議

> 目的：讓未來的弱模型能**安全地**自我更新這套 Harness，而不會把它越改越糟。
> 核心原則：**教訓可自主累積，制度不可自行竄改。** 分級授權如下。

---

## 1. 檔案分級：誰可以動、動之前要不要問 User

| 檔案 | 弱模型可自主更新？ | 條件 |
|------|:---:|------|
| `docs/harness/LESSONS.md`（踩坑紀錄，見 §2） | ✅ 可 | 只能**追加**新條目，用固定格式 |
| `PROJECT_CONTEXT.md`、`PROJECT_PLAN.md` | ✅ 可 | 反映事實變化即可更新；重大方向改變要標註 |
| `docs/harness/A_diagnosis.md` §3「已修復紀錄」 | ✅ 可 | 只追加新的修復事實 |
| `docs/harness/C / D / E`（調度/判準/模板） | ⚠️ 須先問 User | 這是制度骨幹，改動要先徵得同意 |
| `docs/harness/F`（本檔）、`G`（交接信） | ⚠️ 須先問 User | 改「規則的規則」風險最高 |
| `CLAUDE.md` 硬規則（§1）、`.claude/settings.json` deny/hook、`.claude/hooks/*` | ⛔ 一律先問 User | 安全機制，誤改＝拆防護 |
| `.claude/skills/*.md` 格式/位置、`src/` 4 處 loader | ⛔ 一律先問 User | 見 [skills_runtime_assets.md](skills_runtime_assets.md) |

**判準一句話**：改的是「**我學到的事實/教訓**」→ 可自主；改的是「**約束我行為的規則或安全機制**」→ 先問 User。

## 2. 踩坑紀錄（LESSONS.md）寫入格式

踩坑後**立即追加**一條到 `docs/harness/LESSONS.md`（不存在就建）。用這個固定格式，方便日後機器精簡：

```
### [YYYY-MM-DD] 〔一句話標題〕
- 情境：〔在做什麼〕
- 踩到什麼：〔具體現象/錯誤訊息〕
- 根因：〔真正的原因，不是表面症狀〕
- 正解：〔下次該怎麼做，可直接照做的步驟〕
- 標籤：#〔類別，如 skills / permissions / diff / azure〕
```

規則：
- **一坑一條**，根因寫「為什麼」，正解寫「照著做」。
- 不確定根因就標「根因：未確認（假設：…）」，不要編。
- 禁止把整段錯誤堆疊貼進去，只留關鍵行。

## 3. 自動精簡與概念抽象化的觸發條件

`LESSONS.md` 會越長越糟（弱模型會讀不完/失焦）。設定硬門檻：

- **當 `LESSONS.md` 超過 40 條 或 400 行**（先到者為準）→ **觸發精簡**。
- 精簡動作（建議派 Opus 做，見 [C](C_model_dispatch.md)）：
  1. 把同標籤、同根因的多條，**抽象成 1 條「通則」**，移到 `C/D` 對應章節（此步屬「改制度」→ **須先問 User**）。
  2. 已固化為通則的原始條目，移到 `archive/LESSONS_archived_〔日期〕.md`。
  3. `LESSONS.md` 只保留「尚未抽象化」的近期教訓。
- 精簡後回報 User：抽象出哪些通則、歸檔幾條。

---

## 4. 更新安全規則（防止 Harness 自我腐化）

弱模型長期自我更新最大的風險是「**規則漂移**」與「**越權自改**」。強制以下防腐條款：

1. **改任何 `⚠️/⛔` 級檔案前**，先在對話明說「我要改 X，因為 Y」，取得 User 同意才動。
2. **改前必備份 `.bak`**（沿用全專案慣例）。
3. **不得刪除規則**，只能「標記為過時 + 附替代」。刪除是 User 的權力。
4. **新增規則要能被機制執行**才有效：能寫成 permission/hook/script 的，就別只寫在文件裡期望自覺（呼應 [A](A_diagnosis.md) §2 精神）。
5. **每次自我更新後**，在 `LESSONS.md` 或對話記錄「改了什麼、為何、誰授權」，維持可追溯。

> 一句話：**這套制度的修改權，預設在 User 手上；弱模型的自主權，僅限於「累積事實與教訓」。**
