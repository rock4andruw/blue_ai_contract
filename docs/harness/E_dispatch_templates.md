# E. 標準化派工 Prompt 模板

> 用法：主控模型派 subagent 時，**複製對應模板、填空、貼進 Agent tool 的 `prompt`**。
> 每個模板都已內建 [C](C_model_dispatch.md) 的「派工三件套」。填空處以 `〔…〕` 標示。
> 回報格式全共用（見文末），目的是**逼 subagent 只回路徑+行號+結論，不噴大段碼**。

---

## 通用結構（所有模板共用的骨架）

```
【目標】〔一句話說清楚要達成什麼〕
【背景】〔為什麼做；相關檔案路徑（給路徑，不貼內容）；本專案脈絡看 CLAUDE.md〕
【範圍內】〔明確列出可以動的〕
【範圍外｜禁區】不要碰 .env、pic/nda/sla_contract、.claude/skills/*.md、src/.../{negotiate,mas,llm}_service.py 與 verifier.py 的 _SKILLS_DIR 邏輯。不要 git push/部署/刪檔。
【驗收條件（Rubric，逐條可判定）】
  1. 〔客觀條件，如：pytest xxx 全綠〕
  2. 〔…〕
【回報格式】見下方「標準回報格式」，禁止回傳整份檔案或大段程式碼。
【卡住時】同一問題最多試 2 輪；連錯或需動禁區 → 停下回報，附完整錯誤軌跡。
```

---

## 模板 1：搜尋研究（建議 model: haiku / sonnet）

```
【目標】找出〔要找的東西，如：所有呼叫 compare_contracts 的位置〕。
【背景】專案根目錄 /Users/andruw/Documents/bule-ai-team；相關目錄 〔src/services/contract/〕。
【範圍內】唯讀搜尋與閱讀；可跑 grep/rg/glob。
【範圍外｜禁區】不得修改任何檔案；不得讀 .env 與合約目錄。
【驗收條件】
  1. 回報每個命中的〔檔案:行號〕與一句話用途。
  2. 若某處不確定，標「未確認」，不得臆測。
【回報格式】標準格式；「關鍵改動」欄改填「命中清單」。
【卡住時】找不到就明說「未找到，已搜尋範圍：〔…〕」，不要編。
```

## 模板 2：功能實作（建議 model: sonnet）

```
【目標】實作〔功能，如：diff 服務支援 DOCX 空段落〕。
【背景】需求來源〔PROJECT_PLAN.md 第 X 節〕；要改的檔〔src/services/contract/diff_service.py〕；風格見 CLAUDE.md §3。
【範圍內】新增/修改上述檔與其對應測試。
【範圍外｜禁區】通用禁區（見通用結構）；不改公開 API 簽名除非驗收條件要求。
【驗收條件】
  1. 〔pytest tests/test_diff.py 全綠〕。
  2. 新增函式有 type hints + Google-style docstring。
  3. py_compile 通過；既有測試無新增紅燈。
  4. 只動範圍內檔案。
【回報格式】標準格式。
【卡住時】連錯 2 次停下，附錯誤訊息與你的診斷，交回升級。
【驗證要求】你不得自我背書「應該可以」；務必實跑 pytest 並貼出通過證據。
```

## 模板 3：代碼重構（建議 model: sonnet；跨檔權衡用 opus）

```
【目標】重構〔對象〕，行為**必須完全不變**，只改結構。
【背景】動機〔如：抽出重複的 prompt 載入邏輯〕；涉及檔〔清單〕。
【範圍內】等價變換：改結構、命名、抽函式；不改外部行為。
【範圍外｜禁區】通用禁區。特別注意：若涉及 _SKILLS_DIR 讀取邏輯 → 這是禁區，停下問。
【驗收條件】
  1. 重構前後，既有測試全綠且結果一致（行為不變的鐵證）。
  2. 無新增公開介面破壞。
  3. diff 只含結構性改動，無夾帶功能變更。
【回報格式】標準格式；「關鍵改動」說明「搬了什麼、為何等價」。
【卡住時】若發現「不改行為就無法達成」→ 停，這代表不是純重構，回報。
```

## 模板 4：代碼審查（建議 model: opus；務必 Fresh-Context）

```
【目標】審查〔PR/diff/檔案〕，找出正確性 bug 與可簡化/重用/效率問題。
【背景】審查對象〔路徑或 git diff 範圍〕；本專案硬規則見 CLAUDE.md §1。
【範圍內】只讀不改；獨立重新推理，不採信作者的「我驗過了」。
【範圍外｜禁區】不得修改代碼（只出審查意見）；不得讀禁區。
【驗收條件】
  1. 每條發現附〔檔案:行號〕+ 具體失敗情境（什麼輸入→什麼錯誤輸出）。
  2. 依嚴重度排序；區分「確認」與「疑似」。
  3. 沒發現就明說「未發現阻斷性問題」，不硬湊。
【回報格式】標準格式；「關鍵改動」欄改填「發現清單（嚴重度｜檔案:行｜失敗情境）」。
【身分要求】你是全新 context 的挑剔審查員，與實作者隔離（見 C §3）。
```

---

## 標準回報格式（所有 subagent 必須遵守）

```
狀態：完成 / 部分完成 / 卡住
產出檔案：〔路徑清單〕
關鍵改動：〔檔案:行號〕— 〔一句話〕（最多 5 條）
驗收結果：逐條 Rubric → ✅/❌ + 一句證據
卡點（若有）：現象 + 已試過什麼 + 你的診斷
```

> 為什麼強制這個格式：指揮官的 context 很貴。它要的是「你做了什麼、在哪、過了沒」，**不是**你把改動貼一遍。噴大段碼＝浪費雙方 token，且指揮官無法快速核對。
